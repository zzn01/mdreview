# mdreview — Browser-based Review Tool for Markdown Plans

Date: 2026-08-28
Status: Approved design, pending implementation

## Problem

When working with AI coding agents (Claude Code, Cursor, etc.), the agent
frequently produces plan/spec documents in markdown that need human review.
Today this means reading raw markdown in a terminal or editor and typing
feedback back by hand — slow and error-prone. We want a GitHub-PR-style
review experience for a single markdown document, with the feedback flowing
straight back to the agent.

## Goals

- Render a markdown file in the browser and let the reviewer attach inline
  comments to any selected text, plus an overall comment and a verdict
  (approve / request changes).
- Blocking closed loop: the agent invokes the tool, the tool waits until the
  reviewer submits, then the structured feedback is returned on stdout for
  the agent to consume. No manual copy-paste.
- Single static Go binary, no runtime dependencies, usable by any agent that
  can run a shell command.

## Non-Goals (YAGNI)

- Multi-round review state: every review is independent. No snapshots, no
  diff-since-last-review, no comment threads or resolved tracking. The AI
  session already holds prior feedback as context.
- Multi-file review, multiple concurrent review sessions.
- Precise character-level mapping between rendered HTML and markdown source.
  Comments anchor to block-level source line ranges plus the quoted text;
  the server narrows that range by matching the quote against the source
  lines within the block.
- JSON output. Markdown on stdout is sufficient for AI consumption.
- Editing the document in the browser.

## CLI

```
mdreview [flags] <file.md>
mdreview init [--project]

Flags:
  --port N     Listen on a fixed port (default: random free port)
  --no-open    Do not auto-open the browser; just print the URL
  --tunnel     Expose the review on a public https URL via a Cloudflare
               quick tunnel, for review from another device
```

Behavior:

- Starts a local HTTP server bound to `127.0.0.1`, opens the default browser
  at the review page (unless `--no-open`).
- Blocks until the reviewer clicks Submit in the browser.
- On submit: writes the feedback document (see Output Format) to **stdout**
  and exits `0` — for both APPROVE and REQUEST_CHANGES verdicts.
- All logs and the review URL go to **stderr**, so stdout carries only the
  feedback.
- No built-in timeout; lifetime is controlled by the caller. Ctrl-C exits
  non-zero.
- Errors (file missing, requested port busy) exit non-zero with a message on
  stderr.

## Web UI

Single embedded static page (`go:embed`): vanilla JS + CSS, no build step.

- The server renders the markdown to HTML with **goldmark**. Each top-level
  block element is annotated with its source line range
  (`data-lines="42-48"`), taken from the goldmark AST. This is the anchor
  for comments.
- Commenting flow: select any text → a floating "Comment" button appears →
  a comment input opens. Existing comments are listed in a right-hand
  sidebar, aligned with the document; each can be edited or deleted before
  submission.
- A comment records: the source line range of the enclosing block(s), the
  selected text verbatim, and the comment body.
- Bottom bar: an overall-comment textarea plus two submit buttons —
  **Approve** and **Request Changes**.
- Mermaid code blocks are rendered client-side with an embedded
  `mermaid.min.js` (AI plans commonly contain mermaid diagrams).
- Review state (draft comments) lives in server memory: closing the tab
  loses nothing that was already sent to the server; reopening the URL
  restores the session. One review session per process.

## Output Format (stdout)

```markdown
# Review: REQUEST_CHANGES

## Overall
<overall comment, section omitted when empty>

## Comments (2)

### 1. L42-48
> quoted selection from the document
The cache invalidation here has a race; delete the cache before writing.

### 2. L60
> another quoted selection
Rename this section; "misc" hides an important decision.
```

- First line always `# Review: APPROVE` or `# Review: REQUEST_CHANGES`.
- An APPROVE with no comments still prints the header line, so the caller
  gets a definitive verdict.

## Remote review (--tunnel)

`--tunnel` lets a reviewer on another device (typically a phone) reach the
session over the public internet, via a [Cloudflare quick
tunnel](https://developers.cloudflare.com/pages/how-to/quick-tunnel/):

- **Mechanism**: mdreview locates `cloudflared` (on `PATH`, or downloads it
  once to `$UserCacheDir/mdreview` and reuses it thereafter), then spawns
  `cloudflared tunnel --url http://127.0.0.1:<port>`. cloudflared prints a
  random `https://<name>.trycloudflare.com` URL once the tunnel is live;
  mdreview scans for it and discards the rest of cloudflared's own output
  (it never reaches mdreview's stdout/stderr). The tunnel process is killed
  when mdreview exits.
- **Token model**: enabling the tunnel switches the server into token-auth
  mode: a random 16-byte (32 hex char) session token is generated, and
  every request — local or remote — must then present it, either as a
  `?t=` query param or as the `mdreview_token` cookie. A correct `?t=` sets
  the cookie and 302-redirects to the same URL with the token stripped, so
  it doesn't linger in the browser's address bar or history. Token
  comparison is constant-time. This is why token mode also applies to the
  `local` URL mdreview prints — auth is all-or-nothing for the process.
- **Guard extension**: `originHostGuard` normally accepts only loopback
  Host/Origin. In tunnel mode it additionally accepts the tunnel's
  `*.trycloudflare.com` hostname as Host, and `https://<hostname>` as
  Origin — loopback keeps working unchanged, and a plain (non-tunnel)
  server still rejects the tunnel hostname.
- Traffic is TLS from the reviewer's device to Cloudflare's edge, and TLS
  from Cloudflare's edge to the local server, but is **not end-to-end
  encrypted** — Cloudflare can see the document in transit.

## Agent Integration (Claude Code)

The Bash tool has an execution timeout, so the documented calling
convention is **run in background**:

1. Agent runs `mdreview docs/plan.md` with `run_in_background`.
2. Reviewer takes as long as needed; on submit the process exits.
3. The agent is notified of completion and reads the feedback from the
   command's stdout.

The skill is embedded in the binary; `mdreview init` installs it.

## Architecture

```
preview/
  go.mod
  main.go        # flag parsing, startup, browser open, blocking on submit
  server.go      # HTTP handlers: page, comment CRUD, submit
  render.go      # goldmark rendering + source line annotation
  feedback.go    # feedback markdown generation
  tunnel.go      # cloudflared acquisition + quick tunnel for --tunnel
  skillcmd.go    # `init` subcommand: installs the embedded skill
  skill/         # go:embed asset: SKILL.md (the review-plan skill)
  ui/            # go:embed assets: index.html, app.js, style.css, mermaid.min.js
```

- HTTP API (internal to the page): `GET /` rendered page, `GET/POST/PUT/DELETE`
  comment endpoints, `POST /submit` with verdict + overall comment.
- `POST /submit` signals the main goroutine (channel); main prints feedback
  and exits.

## Error Handling

- Missing/unreadable file: exit non-zero before starting the server.
- `--port` busy: exit non-zero (default random port avoids this).
- Browser fails to open: URL is always printed on stderr as fallback.
- Tab closed without submit: server keeps waiting; reopen the URL.
- Every request is checked against its `Origin` and `Host` headers, and
  rejected with `403` unless both name a loopback address; this prevents a
  malicious page or DNS-rebinding attacker from forging comments or a
  submit against the review session.

## Testing

- Go unit tests: feedback formatting, line-range annotation in rendering,
  HTTP handlers via `httptest` covering the full comment-and-submit flow.
- Frontend JS stays thin; verified by manual smoke test.
